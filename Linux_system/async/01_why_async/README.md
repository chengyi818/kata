# 第一章：为什么需要异步编程

## 1. 问题的根源：I/O 等待中的 CPU 浪费

现代计算机中，CPU 的速度与 I/O 设备（网络、磁盘）的速度存在巨大鸿沟：

| 操作 | 延迟 | CPU 周期等价 |
|------|------|-------------|
| CPU 寄存器访问 | ~1ns | 1 cycle |
| L1 缓存 | ~1ns | ~3 cycles |
| 内存访问 | ~100ns | ~300 cycles |
| SSD 读取 | ~100μs | ~300,000 cycles |
| 网络往返 (局域网) | ~500μs | ~1,500,000 cycles |
| 网络往返 (互联网) | ~50ms | ~150,000,000 cycles |

**核心矛盾**：在同步阻塞模型中，当程序发起一个网络请求后，整个线程会被操作系统挂起，
直到数据返回。这段时间里 CPU 完全空转，什么有用的工作都没做。

如果你需要同时处理 1000 个网络连接，传统方案有两种选择：
- **多进程**：每个连接一个进程，但进程创建开销大（~MB 级内存），进程间通信复杂
- **多线程**：每个连接一个线程，开销比进程小但仍然可观（~MB 级栈空间），且线程切换需要内核介入

## 2. 解决方案的演进

```
单线程同步阻塞
     │  并发需求增长
     ▼
多进程 (fork)
     │  进程开销太大，IPC 复杂
     ▼
多线程 (pthread)
     │  线程栈内存开销、上下文切换成本、同步原语复杂度
     ▼
I/O 多路复用 (select → poll → epoll/kqueue)
     │  事件驱动但回调地狱（callback hell），代码逻辑碎片化
     ▼
协程 + async/await
     用同步的写法实现异步的性能
```

### 2.1 多进程/多线程的问题

- **内存开销**：每个线程默认栈大小 8MB（Linux），1000 个线程就是 ~8GB
- **上下文切换成本**：内核态/用户态切换、保存/恢复寄存器、TLB 刷新
- **同步复杂度**：mutex、condition variable、死锁风险

### 2.2 I/O 多路复用

操作系统提供了 `select`/`poll`/`epoll` (Linux) / `kqueue` (macOS/BSD) 等系统调用，
允许单个线程同时监听多个 I/O 事件。这是异步编程的底层基石。

```
用户程序                     内核
   │                          │
   │── epoll_create ────────►│  创建 epoll 实例
   │── epoll_ctl(ADD, fd) ──►│  注册感兴趣的文件描述符
   │── epoll_wait ──────────►│  阻塞等待事件就绪
   │                          │  ...某个 fd 就绪...
   │◄── 返回就绪的 fd 列表 ──│
   │── 处理就绪的 fd ────────│
   │── epoll_wait ──────────►│  继续等待下一批事件
```

但直接使用 epoll 编程会导致「回调地狱」—— 业务逻辑被打散到各个回调函数中，
代码难以阅读和维护。

### 2.3 协程：最佳平衡点

**协程 (Coroutine)** 是一种可以挂起和恢复的函数。与线程的关键区别：

| 特性 | 线程 | 协程 |
|------|------|------|
| 调度方 | 操作系统内核 | 用户态运行时 |
| 切换开销 | 高（内核态切换） | 低（仅保存少量寄存器） |
| 栈大小 | 固定 ~8MB | 按需分配，通常 KB 级 |
| 并发数 | 通常 < 10K | 可达百万级 |
| 抢占性 | 抢占式 | 协作式（主动让出） |

**async/await** 是协程的语法糖，让你用看起来像同步的代码写出异步的逻辑：

```python
# 同步写法（阻塞）
def fetch_data():
    response = requests.get("https://example.com")  # 线程在此阻塞
    return response.text

# 异步写法（非阻塞）
async def fetch_data():
    response = await aiohttp.get("https://example.com")  # 协程在此挂起，让出 CPU
    return response.text
```

两种写法的**逻辑结构完全相同**，但异步版本在等待网络响应时会让出 CPU，
允许同一个线程去执行其他协程任务。

## 3. 运行本章示例

本章包含三个 Python 脚本，用模拟 I/O 延迟的方式定量对比三种并发模型的性能：

```bash
# 1. 同步阻塞 —— 串行执行，总耗时 = 单次耗时 × 任务数
python blocking_io.py

# 2. 多线程 —— 并行执行，总耗时 ≈ 单次耗时，但线程有额外开销
python multithread_io.py

# 3. 异步 —— 协程并发执行，总耗时 ≈ 单次耗时，开销最小
python async_io.py
```

观察输出中的耗时对比，体会三种方案的差异。

## 4. 关键概念总结

- **并发 (Concurrency)** vs **并行 (Parallelism)**：
  并发是逻辑上同时处理多个任务（可以在单核上交替执行），并行是物理上同时执行多个任务（需要多核）。
  异步编程主要解决的是 I/O 并发问题。

- **阻塞 (Blocking)** vs **非阻塞 (Non-blocking)**：
  阻塞调用会挂起线程直到操作完成；非阻塞调用会立即返回，通过其他机制（回调、轮询、await）获取结果。

- **Future/Promise**：一个代表「尚未完成的计算结果」的占位符对象。
  你可以对它 await，等到结果就绪时再继续。

- **Event Loop**：异步运行时的核心调度器。不断循环执行：
  1. 检查哪些 I/O 操作已就绪
  2. 恢复对应的协程继续执行
  3. 当协程再次遇到 await 时挂起，回到步骤 1
