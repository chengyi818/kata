# PARA 知识管理策略设计

## 一、PARA 简介

PARA 是由 Tiago Forte 提出的知识管理框架，将所有信息分为四大类：

| 分类 | 含义 | 特征 |
|------|------|------|
| **P**rojects（项目） | 有明确目标和截止日期的短期任务 | 有终点、可完成 |
| **A**reas（领域） | 需要长期维护的职责范围 | 无终点、持续维护 |
| **R**esources（资源） | 持续感兴趣的主题参考资料 | 按主题聚合、随时引用 |
| **A**rchive（归档） | 以上三类中不再活跃的内容 | 冷数据、可追溯 |

---

## 二、团队组织结构映射

```
4级部门（~100人）
├── XM团队 A（~30人）
│   ├── PL组 A-1
│   ├── PL组 A-2
│   └── PL组 A-3
├── XM团队 B（~30人）
│   ├── PL组 B-1
│   └── PL组 B-2
└── XM团队 C（~30人）
    ├── PL组 C-1
    └── PL组 C-2
```

**关键原则**：知识目录结构与组织结构解耦，按 PARA 分类而非按团队分文件夹，避免信息孤岛。

## 四、各分类详细说明

### 1. Projects（项目）

> 有明确目标、有截止日期、会结束的工作。

**适用内容**：
- 某次系统改造的方案设计与执行记录
- 季度专项攻坚（如性能优化、安全加固）
- 新产品/新功能的交付过程文档

**命名规范**：`[YYYY-QN] 项目名称`

**项目文件夹内部结构**：
```
[2026-Q1] XX系统性能优化/
├── README.md          # 项目概述、目标、负责人、时间线
├── 方案设计/
├── 会议纪要/
├── 进展跟踪/
└── 复盘总结.md
```

**生命周期**：项目完成后，整个文件夹移入 `Archive/YYYY/Projects/`。

---

### 2. Areas（领域）

> 没有终点、需要持续维护的长期职责。

**适用内容**：
- 业务知识（核心流程、产品逻辑、术语定义）
- 技术规范（编码规范、架构准则、发布流程）
- 新员工入门（通用 + 各 XM 团队专属）
- 运维手册（部署、监控、故障处理）

**维护规则**：
- 每篇文档标注 `负责人` 和 `最后更新日期`
- 每季度由各 PL 组审查一次所属领域文档的准确性
- 新员工入门手册在每次流程变化后 **即时更新**

---

### 3. Resources（资源）

> 按主题组织的参考资料，无特定时效性。

**适用内容**：
- 团队内部技术分享的沉淀
- 外部收集的优质文章、博客、报告
- 学习路径与推荐书单
- 行业知识与竞品分析

**维护规则**：
- 鼓励全员贡献，门槛低、审核轻
- 每条资源标注 `来源`、`推荐人`、`标签`
- 半年未被访问的资源移入 Archive

---

### 4. Archive（归档）

> 不再活跃但仍有参考价值的历史内容。

**适用内容**：
- 已完成的项目文档
- 过时但有参考意义的技术方案
- 不再维护的旧版规范

**规则**：
- 按年份组织：`Archive/YYYY/`
- 归档不等于删除，仍可全文检索
- 年度清理时对超过 2 年的归档内容做一次评估

## 五、运营机制

### 5.1 角色与职责

| 角色 | 范围 | 职责 |
|------|------|------|
| **知识库 Owner**（1人） | 4级部门 | 制定整体策略、定期审计、推动文化 |
| **XM 知识负责人**（每 XM 团队 1人） | XM 团队 | 维护本团队 Areas 内容、推动团队贡献 |
| **PL 知识联络人**（每 PL 组 1人） | PL 组 | 确保组内文档及时更新、收集新员工反馈 |
| **全体成员** | 个人 | 贡献 Resources、维护自己负责的文档 |

### 5.2 文档生命周期

```
创建 → 评审 → 发布 → 定期维护 → 归档/删除
                         ↑
                   季度 Review 触发
```

### 5.3 定期活动

| 频率 | 活动 | 说明 |
|------|------|------|
| 每周 | 知识分享 Slot | XM 团队轮流安排 15 分钟知识分享，沉淀到 Resources |
| 每月 | 新增文档 Review | XM 知识负责人审查当月新增内容的质量与分类 |
| 每季度 | Areas 健康度检查 | 各 PL 组检查负责领域文档是否过期 |
| 每半年 | Resources 瘦身 | 清理低价值资源至 Archive |
| 每年 | 全库盘点 | 知识库 Owner 主导年度回顾，调整目录结构 |

### 5.4 新员工入门流程

```
Day 1:  阅读 Areas/团队管理/新员工入门/入职指南（通用）.md
Day 1:  完成 Areas/团队管理/新员工入门/开发环境搭建.md
Day 2:  阅读 Areas/团队管理/新员工入门/各XM团队专属入门/XM-X 入门手册.md
Day 3:  浏览 Areas/业务知识/ 了解核心业务
Day 5:  浏览 Areas/技术规范/ 了解编码与发布流程
Week 2: 认领一篇文档进行补充或纠错（破冰贡献）
```

## 六、工具建议

| 需求 | 推荐工具 | 说明 |
|------|----------|------|
| 文档编写与协作 | 语雀 / Confluence / Notion | 支持多人协作、权限控制、全文搜索 |
| 文档即代码 | Git + Markdown | 适合技术规范类文档，可与代码仓库联动 |
| 搜索与发现 | 工具自带搜索 + 标签体系 | 确保任何人 3 次点击内找到所需文档 |
| 模板管理 | 内置模板库 | 降低写作门槛，保持格式一致 |

## 七、文档模板（通用）

每篇文档的头部应包含以下元信息：

```markdown
---
title: 文档标题
category: Projects | Areas | Resources
tags: [标签1, 标签2]
owner: 负责人姓名
team: XM团队名 / PL组名
created: YYYY-MM-DD
updated: YYYY-MM-DD
status: draft | published | archived
---
```

## 八、落地路线图

| 阶段 | 时间 | 目标 |
|------|------|------|
| **第一阶段：搭骨架** | 第 1-2 周 | 建立 PARA 目录结构，指定各级负责人，编写模板 |
| **第二阶段：填内容** | 第 3-6 周 | 各 XM 团队迁移/创建 Areas 核心文档，完成新员工入门手册 |
| **第三阶段：跑起来** | 第 7-10 周 | 启动周分享、月 Review 机制，全员开始贡献 Resources |
| **第四阶段：持续优化** | 第 11 周起 | 根据使用反馈调整结构，执行首次季度 Areas 健康度检查 |

---

## 九、成功指标

- 新员工从入职到独立上手时间缩短 **30%**
- 团队成员查找知识的平均时间不超过 **3 分钟**
- 每季度活跃文档（有更新）占比 **> 60%**
- 每人每季度至少贡献 **1 篇** Resources 内容
